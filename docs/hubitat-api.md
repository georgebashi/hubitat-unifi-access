# Hubitat integration notes

## Recommended shape

Ship one installable parent Groovy app and a child door device driver. The app owns hardware discovery, UniFi credentials, async requests, polling, and child lifecycle. It creates one child per Access door using a stable DNI such as `unifi-access:<door-id>` and `addChildDevice(namespace, driverName, dni, [label: doorName])`; reconcile children by DNI and retain missing children as unavailable/stale so existing automations keep their references. Hubitat's [official parent/child driver example](https://github.com/hubitat/HubitatPublic/blob/master/examples/drivers/genericComponentParentDemo.groovy) demonstrates stable DNIs, `addChildDevice`, lookup, and event delivery. Apps also expose child-device methods in the [App Object API](https://docs2.hubitat.com/en/developer/app-object).

The door driver emits `ContactSensor` observations only when `door_position_status` is present; translate `open` / `close` to `open` / `closed`, and preserve the last reported value with a stale marker when API data is absent. Hubitat ContactSensor has no `unknown` enum value. Retain missing API resources as stale children rather than deleting them, so user automations do not silently lose referenced devices. The agreed native `Lock` mapping is momentary `unlock()` and `lock()` via Access `lock_now`, ending active scheduled/temporary unlocking. Native lock state follows relay observations, or `unknown` when unavailable. See [native mappings](native-capabilities.md) and Hubitat's [driver capability reference](https://docs2.hubitat.com/en/developer/driver/capability-list).

## HTTP, TLS, and schedules

Use Hubitat `asynchttpGet` / `asynchttpPost` (or async PUT/PATCH as the UniFi endpoint requires), with callbacks to parse results and update child events. The [Common Methods API](https://docs2.hubitat.com/en/developer/common-methods-object) documents asynchronous HTTP methods and request maps. Include bounded timeouts, handle HTTP and transport errors in callbacks, and avoid blocking synchronous network calls in a hub app.

For an Access controller with a self-signed local HTTPS certificate, Hubitat's HTTP request map supports `ignoreSSLIssues: true`; use it only when needed, since it disables certificate validation for that request. The option is confirmed in this [Hubitat HTTPS troubleshooting thread](https://community.hubitat.com/t/cant-get-get-to-work/136365), and Hubitat's [HTTP example driver](https://github.com/hubitat/HubitatPublic/blob/master/examples/drivers/httpGetSwitch.groovy) is a first-party implementation reference. Use `runEvery1Minute`/`runEvery5Minutes` or a configurable `runIn` schedule in the app, and cancel old schedules before reconfiguration/uninstall; the [App Object API](https://docs2.hubitat.com/en/developer/app-object) documents scheduling methods. The [Access API PDF](https://assets.identity.ui.com/unifi-access/api_reference.pdf) specifies HTTPS port `12445`, bearer API token authorization, and a self-generated/untrusted server certificate.

Hubitat has a WebSocket **client** interface, so a Groovy driver may connect outward to a compatible server; the [WebSocket interface](https://docs2.hubitat.com/en/developer/interfaces/websocket-interface) is not a server/listener for UniFi to connect to. UniFi's API supports WebSocket notifications and webhook endpoint CRUD; receiving UniFi webhooks requires an inbound Hubitat app endpoint reachable from the controller. Prefer polling for first-milestone state, then assess the API's WebSocket client for push updates. Hubitat's WebSocket implementation may accept `ignoreSSLIssues: true` for a self-signed `wss://` peer ([community-confirmed](https://community.hubitat.com/t/driver-connecting-to-insecure-url/119642)); confirm against the target hub version.

## Installation credentials and Maker API

An app/driver package installs as Hubitat Groovy code through the hub's Apps Code / Drivers Code flow or HPM; install-time authentication is the hub UI session. HPM's initial setup asks for the Hubitat admin credentials only when Hub Security is enabled. HPM's upstream [developer documentation](https://hubitatpackagemanager.hubitatcommunity.com/devs1.html) says packages consist of a package manifest plus a repository index; its [manifest format](https://hubitatpackagemanager.hubitatcommunity.com/pkgManifest.html) lists metadata and `apps` / `drivers` entries. Use one required app entry and one required driver entry, each with stable UUID `id`, `name`, `namespace`, raw Groovy `location`, and `required: true`; set app `oauth: false` unless the app itself exposes OAuth-protected HTTP endpoints. The current upstream [HPM repository](https://github.com/HubitatCommunity/hubitatpackagemanager) contains the manifest and repository examples.

Maker API is not required for this integration: it is Hubitat's REST surface for **external** clients to read/control authorized Hubitat devices, while this app runs inside the hub and creates its devices directly. Hubitat's [Maker API overview](https://hubitat.com/home-automation/maker-api) describes that external-app use. Runtime credentials are the UniFi Access API credentials entered in the app preferences; do not request a Hubitat Maker API token. If later adding an inbound webhook endpoint, use Hubitat's app endpoint/OAuth mechanism instead of Maker API unless the webhook sender specifically needs Maker API's external device interface.

## Verified references

- [Hubitat developer documentation](https://docs2.hubitat.com/en/developer): app/driver APIs, common methods, scheduling, capabilities, and interfaces.
- [HubitatPublic example drivers](https://github.com/hubitat/HubitatPublic/tree/master/examples/drivers): first-party Groovy examples, including child devices and HTTP.
